## Approved architectural decisions (do not change without explicit re-approval)

- **No protected roles.** Every role, including the three built-in ones, is fully editable/cloneable/deletable.
- **Protect the permission, not a role name.** "ניהול תפקידים והרשאות" (`electionDay.manageRolesAndPermissions`) must always be held by at least one user - enforced at the DB/RPC level in a future phase, not just client-side.
- **Deleting a role with assigned users is always blocked** - no auto-reassignment, no cascading user deletion. Enforced today at the DB level via `ON DELETE RESTRICT` (Phase 0).
- **"ניהול תפקידים והרשאות" is separate from "ניהול הרשאות משתמשים"** (`electionDay.manageUsers`) - two independent permissions.
- Role fields: name, description, **scope** (תחום עבודה: "כל אנשי הקשר" / "רק המוקצים לי" today, modeled as `scope_type` + reserved `scope_value` so a future dimension, e.g. geographic, is additive, not breaking). "Scope" as a word is never shown in the UI.
- "Clone role" is a required capability.
- Editing an existing user's role is out of scope (stays delete + recreate).
- **Core principle**: the system only knows permissions. `manager`/`operations`/`voting`/any future role are just named permission bundles - there is no "role type" concept in code.
- `legacy_role_key` was a temporary migration-bookkeeping anchor only (removed entirely in Phase 3, see below) - it never participated in any permission/scope decision itself, and was never shown in any UI or touched by role editing while it existed.
- Every migration wrapped in explicit `begin;`/`commit;` (the Supabase CLI pipelines a file's statements, it does not implicitly wrap them in a transaction).
- Rollout was 4 independent, individually testable/deployable/rollback-able phases - no big-bang cutover. All 4 are now shipped.

## Coordinator Delete ("הסר אחראי") - IMPLEMENTED and verified (local Docker only), safe edit+remove guard - uncommitted

Investigated adding a genuine `הסר אחראי` action to Allocation Management, distinct from `העבר הקצאות`/`סיום פעילות`. **Not implemented - correctly stopped before any DB/RPC/schema change, both times this was investigated (2026-08-21).**

**What already exists**: the `remove` action is already fully wired end-to-end at the application layer - `CoordinatorAction`'s TS type already includes `"remove"`, `toCoordinatorActionPayload` already maps it, `manageCoordinators()` already sends it to `election_day_manage_coordinators_v2`, and that RPC already has a `remove` branch (`elsif v_action_type = 'remove' then ... delete from election_day_coordinators ...`). No UI button calls it yet - that's the only missing piece at the application layer.

**Why it can't safely ship as-is**: the RPC's own safety gate for `remove` is `election_day_has_allocation_activity()` - a **global**, one-way, all-coordinators flag ("has ANY `election_day_coordinator_operations` row ever been written, for ANY coordinator"), not a per-coordinator check. This is the wrong predicate for the stated requirement in two directions at once: (1) it never checks whether voters are currently assigned to *this* coordinator via `election_day_voters.coordinator` (a plain free-text column, no FK to `election_day_coordinators` by original design - confirmed by rereading `20260811100000_election_day_coordinator_nullable.sql`'s own comment) - a coordinator that received voters purely via CSV import/coordinator-sync (never through an allocation/rebalance/end RPC) could be deleted while still holding real assigned voters; (2) once the global flag trips even once, `remove` is permanently blocked for *every* coordinator forever after, including one added by mistake seconds ago with zero history of its own - directly contradicting the stated "typical case: added by mistake, never used" requirement. **Verified this isn't hypothetical**: a direct read-only Production query (`select count(*) from election_day_coordinator_operations`) returned **1** - the global flag is already tripped in Production right now, so the existing `remove` action, if wired up today, would immediately and permanently fail with `COORDINATOR_LOCKED` for every coordinator, with no way to distinguish a genuinely-safe one.

**The correct predicate**, from the real architecture (not guessed): a coordinator is safe to physically delete iff **both** (a) `NOT election_day_coordinator_participated(coordinator_id)` - a **per-coordinator** boolean RPC that already exists and is already granted to `anon`/`authenticated` (used today for `link`/`unlink`/`relink` gating), checking whether this specific coordinator was ever a `from`/`to` in `election_day_coordinator_operation_items` or the `subject` of an `election_day_coordinator_operations` row; and (b) `NOT EXISTS (select 1 from election_day_voters v where v.coordinator = <this coordinator's display_name>)` - no voter currently free-text-matches this coordinator, covering the import-only-assignment gap (a) misses.

**Minimal proposed DB/RPC design** (not built, pending separate approval): a migration that `create or replace`s `election_day_manage_coordinators_v2`'s `remove` branch to swap its guard from the global `election_day_has_allocation_activity()` to the per-coordinator pair above (condition (a) already has a ready-made function; condition (b) is a one-line inline `EXISTS`, no new function needed) - same signature, same permission gate (`electionDay.manageCoordinatorAllocation` via reauth proof), no schema/column/FK/RLS change.

**Concurrency - re-investigated and resolved (2026-08-21, second pass)**: the earlier report left this as an open question, reasoning from `election_day_manage_coordinators_v2`'s ORIGINAL (20260813120000) definition, which indeed did not take the global `election_day_voter_allocation_mutation` advisory lock. That's now stale - rereading the migration history in full found `20260820000000_election_day_import_coordinator_sync.sql` (the Coordinator Sync checkpoint, already live in Production) **extended this exact function to also acquire that lock**, closing a different TOCTOU gap (the coordinator-sync-on-import step). The CURRENT live definition takes `pg_advisory_xact_lock(hashtext('election_day_voter_allocation_mutation'))` immediately after the auth/permission check and before the coordinator-row `FOR UPDATE` lock - the exact same lock, same position, every other allocation-mutation RPC (rebalance/initial-allocation/end/import) already uses. **This means the proposed `remove` fix needs no new lock at all** - a new voter-assignment `EXISTS` read added inside the `remove` branch would already run fully serialized against every concurrent business RPC, since none of them can be mid-transaction past this same advisory lock at the same time. No deadlock risk either: every RPC that touches this lock acquires it as a single global mutex *before* any row-level lock, in the same relative order, every time - two competing calls always fully serialize at the advisory-lock step itself, never interleave their row-lock acquisition. **"Do not invent a separate lock" is satisfied by construction: the existing lock is already exactly right, already in place, nothing to add.**

**Error-code question** (reuse `COORDINATOR_LOCKED` for both the participation and voter-assignment cases, vs. a new distinct code e.g. `COORDINATOR_HAS_ASSIGNED_VOTERS`) is a minor product/copy decision, left open for whoever approves the migration.

**UI design** (described, not built - per the task's explicit "prepare the design, do not wire it to an unsafe RPC" instruction): a third `הסר אחראי` button on each active coordinator's row, visually distinct from `העבר הקצאות`/`סיום פעילות` (destructive styling); clicking it first checks the safe-delete predicate (client can already read `election_day_coordinator_participated` and the same `coordinatorStats.totalAssigned` it already has for every other roster row); if ineligible, a concise inline reason is shown and the manager is pointed at `העבר הקצאות`/`סיום פעילות` instead, no RPC call made; if eligible, a confirmation dialog requires typing the coordinator's exact name before the (then-fixed) RPC's `remove` action is sent.

**Identity-safety re-investigation (2026-08-21, third pass) - found a real gap, STOPPED before authoring the migration**: the task's mandatory pre-migration identity check asked three specific questions about `election_day_voters.coordinator = election_day_coordinators.display_name`, answered by rereading the actual schema/RPC bodies rather than assuming:

- **Display-name uniqueness**: only a **partial** unique index - `election_day_coordinators_active_display_name_key on (display_name) where status = 'active'`. At most one *active* coordinator can hold a given name at any moment, but an *ended* coordinator's name is free to be reused by a brand-new one - by design (`20260811100100`'s own comment: "ending and re-adding the same person next election day is never blocked by a stale row").
- **Rename behavior - the actual finding**: rename is a real, live, UI-wired feature (`CoordinatorRosterEditor.tsx`'s inline edit, `confirmEditClick` → `action: "edit"` → `election_day_manage_coordinators_v2`'s `edit` branch, `update election_day_coordinators set display_name = ... where id = ...`). **This `edit` never touches `election_day_voters.coordinator`** - confirmed by reading the full RPC body; only the three real allocation RPCs (`apply_initial_allocation_v2`/`rebalance_assignments_v2`/`end_coordinator_activity_v2`) write `election_day_voters.coordinator`, always stamping it with the acting coordinator's *display_name at that moment*. `edit`'s own guard is the same global `election_day_has_allocation_activity()` flag as `remove` - meaning rename is only reachable in the pristine window *before the first-ever allocation/rebalance/end operation in the whole session*, but that window is real and commonly hit: `election_day_sync_coordinators_from_voters()` (the automatic import-time coordinator backfill, confirmed by rereading its migration) auto-creates a coordinator entity for every distinct `voters.coordinator` string **without ever setting `linked_assignment_name`** and without writing any `election_day_coordinator_operations` row - so a coordinator auto-synced right after import, already the free-text owner of real assigned voters via raw string match, can still be renamed via `edit` at that point with zero participation recorded.
- **Identity reuse / stale-name ambiguity - the concrete unsafe sequence proven reachable**: (1) import lands voters with `coordinator = 'רחל'`; (2) the import's own sync auto-creates coordinator A, `display_name = 'רחל'`, `linked_assignment_name = null`, zero operations recorded; (3) before any real allocation ever runs anywhere in the session, a manager renames A via `edit` to `'שרה'` (unblocked - no activity yet); (4) the `'רחל'`-labeled voter rows are **not** updated by step 3 - `edit` never cascades to `election_day_voters`; (5) checking the proposed safe-delete predicate against A now - `NOT election_day_coordinator_participated(A.id)` → true (A genuinely never ran an allocation op); `NOT EXISTS (voters where coordinator = A.display_name)` → checks `coordinator = 'שרה'`, finds **zero** matches (the real assigned voters still say `'רחל'`) → **the predicate wrongly reports A as safe to delete**, even though A is the entity that owns those `'רחל'`-labeled voters in every way the rest of the app (dashboard breakdown, coordinator scoping) actually treats as "assignment." Deleting A at that point silently orphans the free-text label with no coordinator entity behind it, and a later coordinator that happens to reuse the name `'רחל'` (freely allowed once A is gone / once A never held it as `status = 'active'` under that name) would appear to "inherit" those voters with zero real relationship to A's history - exactly the ambiguity the task asked to rule out, and it is not ruled out.
- **Why this wasn't caught by the two earlier passes**: both prior investigations reasoned about `remove` in isolation (participation-check correctness, then lock/concurrency correctness) and never traced whether a *different* action (`edit`) could invalidate `remove`'s own name-based predicate between the check and any future delete - the gap is at the seam between two actions, not inside `remove` itself.

**STOP condition met, per the task's own explicit instruction ("if the text-name relationship is not provably safe... STOP before creating any migration")**: the identity relationship is **not** provably safe for a "modify only the `remove` branch" fix, because closing the gap requires the *same* per-coordinator "not currently assigned" predicate to also gate `edit` (rename) - a coordinator must not be renameable away from a name that still has voters currently matching it, or the exact stale-old-name scenario above stays open. That is a two-branch change, wider than the "CREATE OR REPLACE, modify only the `remove` behavior" scope this task pre-authorized - so it is reported here as an open design question, not built.

**Smallest professional solution** (schema/FK-redesign-free, as required): extend the identical `NOT election_day_coordinator_participated(id) AND NOT EXISTS (voters where coordinator = display_name)` gate to **both** `remove` and `edit` in the same `create or replace` of `election_day_manage_coordinators_v2` - renaming a coordinator that currently has zero free-text-matching voters is unaffected (the common case: fixing a typo moments after adding, before any voter has been linked/imported against it); renaming one that *does* have currently-matching voters is blocked with a clear reason (e.g. reuse `COORDINATOR_LOCKED`, or a new `COORDINATOR_HAS_ASSIGNED_VOTERS`), forcing the manager to reassign/unlink first - eliminating the seam the unsafe sequence above depends on. No new lock needed (same reasoning as the second pass - the existing `election_day_voter_allocation_mutation` advisory lock already covers the whole action-processing loop, `edit` included). No schema/FK/RLS change of any kind.

**Status: NOT READY for migration approval as previously scoped ("remove-only")** - the per-coordinator predicate, minimal diff shape, and concurrency behavior are all correct and unchanged from the second pass, but the fix must additionally touch the `edit` branch to be genuinely safe; that's an explicit scope decision for whoever approves this (extend to both branches, or accept the residual gap and document it as a known limitation instead - both are legitimate calls, just not this session's to make unilaterally). **No code was written for this fix** - investigation and this design report only, all three times.

## Election Day Layout - inconsistent white gap beside the sidebar - VERIFIED root cause, fixed (local, uncommitted)

A user report that the white gap next to the fixed right sidebar changes size when moving between Election Day screens was investigated structurally, not patched blindly.

**Ruled out first** (each independently, all 6 top-level routes plus the Allocation Management sub-view measured live via Playwright against local Docker at 1920px, geometry byte-identical across every one - `contentWidth: 1400`, `gapNextToSidebar: 132` in every case, zero variance): a per-route width/margin override (none exists - `ElectionDayShell.tsx`'s single `<div className="mx-auto max-w-[1400px]">` wraps every route's `<Outlet>` uniformly, including the Files page's conditionally-rendered `CoordinatorAllocationView`, which has no width wrapper of its own and simply inherits the shared one); a route-transition loading-state flash; any known service-worker/PWA mechanism (none exists anywhere in this codebase, already ruled out during the prior Production-UI-mismatch investigation this same day).

**VERIFIED root cause**: `AppShell`'s layout scrolls at the **document level** (the sidebar's `sticky top-0 h-dvh` positioning only makes sense against that scrolling context - confirmed no inner `overflow-y-auto` container exists anywhere in the shell), and `src/index.css` had no `scrollbar-gutter` reservation anywhere. On a real (non-headless) browser that reserves layout space for a visible scrollbar (the Windows Chrome default), a page tall enough to need a vertical scrollbar leaves less horizontal space for content than a shorter page at the identical viewport width - shifting the `mx-auto max-w-[1400px]` centered block, and with it the visible gap next to the sidebar, by the scrollbar's width, specifically on every navigation that crosses the "needs a scrollbar" threshold. **Caveat, stated honestly**: this session's headless Chromium renders with overlay (non-space-consuming) scrollbars, so the exact pixel shift could not be empirically reproduced in this environment even after deliberately forcing a 3000px-tall dummy element and re-measuring (result: 0px shift, confirming headless-here doesn't reserve gutter space at all, not that the mechanism is absent on a real browser). The diagnosis rests on structural code-level proof (document-level scroll + zero gutter reservation, the one remaining candidate after every other structural cause was directly measured and ruled out), not a reproduced screenshot diff.

**Fix**: one line, `scrollbar-gutter: stable;` added to the existing `html` rule in `src/index.css`'s `@layer base` block - reserves the scrollbar's gutter unconditionally, so content width (and the sidebar gap) stays constant regardless of whether any given page's content happens to overflow the viewport height. No page content touched, no per-page change, single shared-layout fix as required. Well-supported (Chromium 94+, Firefox 97+, Safari 18+); degrades to today's existing behavior on anything older, never worse.
