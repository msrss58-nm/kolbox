## 2026-08-23 - Multi-Tenant Program: Phase B3 plan approved, Phase 0 (Platform Foundation) implemented locally

**Status: LOCAL ONLY - not pushed, not deployed, no migration applied to Production.** A new, separate initiative from the Election Day UX work below: a staged plan to migrate KolBox's currently single-tenant Election Day system to a Multi-Tenant architecture (Platform Owner / Election Workspace / Election Owner / Multi-Entity Owner as new principals, `workspace_id` on every Election-Day table, deny-by-default RLS enforced server-side). The full architecture and staged Expand→Backfill→Cutover→Contract implementation plan were produced and approved this session (in-conversation reports, not yet a standalone doc) after a live re-audit of the actual repository (schema/RLS/migrations, auth/session/permissions, RPC/business-logic, frontend/routes/storage). Two corrections were applied before approval: ordinary Election Day usernames are already globally unique, so login never needs a workspace slug/code - the server resolves `username → PermissionUser → workspace_id` entirely server-side; and the pending-Owner-access table carries no password/credential material of any kind, since Supabase Auth is the sole credential store. The one open product decision (session expiry for a login that happens *after* the workspace's election has already ended) is now resolved: such a session expires 8 hours after that login, rather than at a past `election_end_at` - the existing "expires at END" rule for a pre-END login, and "END never locks the system," are both unchanged.

**Phase 0 (Platform Foundation) implemented and verified locally**: 7 new, currently-empty tables (`platform_owners`, `election_workspaces`, `election_workspace_pending_owner_access`, `election_owners`, `multi_entity_owner`, `multi_entity_assignments`, `platform_deletion_audit`), purely additive - zero change to any existing Election Day table/RLS/RPC/frontend behavior. RLS-enabled with zero policies/grants on every table (deny-by-default). `election_workspace_pending_owner_access` has no password field; `election_workspaces` has no stored status column (lifecycle is derived from `election_end_at`, never stored); `multi_entity_owner` is a true singleton (same idiom as `election_day_settings`).

**Verification**: a new 42-check regression (`scripts/smoke-multi-tenant-phase0-schema.ts`), live RLS/constraint/grant introspection against local Docker, a disposable functional test proving the singleton rejection and cascade-delete both work correctly (fully cleaned up after), an isolated fresh-replay proof that all 50 migrations apply cleanly from empty, `tsc -b`/`npm run build` clean, and a representative sample of existing smoke tests re-run with zero regression (one pre-existing, unrelated, already-documented failure in `smoke-permissions.ts` confirmed unchanged, not touched). All 15 protected scripts confirmed untouched. See `CURRENT_STATUS.md` and `task-plan.md`'s Progress Log for full detail.

## 2026-08-21 - Election Day: Allocation Rebalance UX clarification + coordinator grant least-privilege fix

**Status: CLOSED (2026-08-21 update).** Pushed to `origin/master`, and the grant-fix migration is applied to Production - see "Election Day: Production Rollout" above for the full rollout record. Production's over-grant on `election_day_coordinators` is now remediated (`anon`/`authenticated` hold exactly `SELECT`).

A report that `ניהול הקצאות → העברת הקצאות` (partial mid-day rebalance between active coordinators) "appears to require ending the source coordinator" was investigated end-to-end. **The rebalance business logic itself was already correct** - `election_day_rebalance_assignments_v2` is a fully separate RPC from `election_day_end_coordinator_activity_v2`, never writes `status`, and moves only "remaining" (not voted/closed) voters by exact quantity - verified live with disposable data: a partial transfer left both the source and destination coordinators `active`, moved only eligible voters, and never invoked the end-coordinator RPC. No allocation/rebalance/end-coordinator logic was changed.

**A real, separate bug was found instead, while proving the above live**: `public.election_day_coordinators` has a permissive RLS `SELECT` policy (`to anon, authenticated`, `using (true)`) but its creating migration (`20260811100100_election_day_coordinators_table.sql`) never granted the underlying table-level `SELECT` the policy depends on. A fresh local Docker replay of every tracked migration gets `42501: permission denied for table election_day_coordinators` on every `listCoordinators()` call - `coordinators` never resolves, and the entire Allocation Management screen (Setup, Live view, Rebalance, End) renders blank locally with no error surfaced anywhere. Direct read-only verification against the linked Production project (`supabase db query --linked`) found Production is **not** missing the grant, but holds a far broader one than ever intended - `SELECT, INSERT, UPDATE, DELETE, REFERENCES, TRIGGER, TRUNCATE`, granted by `postgres` with no audit trail - the signature of a manual out-of-band `GRANT ALL` (Studio table editor default, or a direct SQL-editor fix) applied at some point and never captured in a tracked migration. Confirmed migration/Production drift, with Production ahead of (broader than) the repo's own history. No INSERT/UPDATE/DELETE policy exists on the table anywhere, so RLS's deny-by-default behavior means this broader grant has had zero operational effect to date - just unnecessary standing privilege.

Before any fix, confirmed no legitimate application path depends on direct table-level write privileges on this table: the only reference anywhere in `src/` is `listCoordinators()`'s own `SELECT`, plus a read-only Realtime subscription; none of the 16 protected `scripts/*` files reference the table at all; all 4 real mutation RPCs are `security definer` and run as their owner, never as the caller.

**Fix**: new migration `20260821020000_election_day_coordinators_grant_fix.sql` - `revoke insert, update, delete, truncate, references, trigger ... from anon, authenticated;` then `grant select ... to anon, authenticated;`. Least-privilege, matches the table's own originally-documented design intent, does not reproduce Production's accidental over-grant. **Applied to local Docker first, then to Production on 2026-08-21** (re-verified directly against the linked project: exactly `SELECT` for `anon`/`authenticated`, all 6 broader privileges confirmed revoked, RLS policy unchanged).
