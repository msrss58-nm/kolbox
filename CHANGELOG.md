# Changelog

Notable changes to KolBox, in reverse chronological order.

## 2026-08-06 - Election Day: Dynamic Non-Voting Reasons

**Status: production deployment complete.** Shipped as commit `2c92470` ("feat: add dynamic non-voting reasons"), pushed to `origin/master`, deployed to `https://kolbox-gamma.vercel.app` (deployment `dpl_4qBm7TmR7F3WH62UQ7PMNeMonmYd`, `target: production`, `readyState: READY`). 3 migrations applied to the linked remote database (`election_day_not_voting_reasons_table`, `election_day_voters_not_voting_reason_column`, `election_day_not_voting_reasons_rpc`).

Replaces the previous binary "הצביע"/"לא הצביע" with a fully dynamic, admin-managed catalog of non-voting reasons (create/edit/disable/reorder/delete-if-unused), seeded with 6 example reasons as ordinary editable data - not hardcoded. A voter's contact modal gets a reason dropdown (shown only while not voted, storing only the reason's id); the reason is never cleared once a voter is later marked "הצביע" - it stays in the database for history/future reporting, it just stops being offered for editing. Backward-compatible by design: the `voted` mechanism, election day core flow, and the existing `manager`/`operations`/`voting` permission engine are all untouched.

- **New table + RPCs**: `election_day_not_voting_reasons` (RLS enabled, zero policies - deny-all direct access, same pattern as `election_day_roles`), 6 `SECURITY DEFINER` RPCs (`list`/`create`/`update`/`set_active`/`delete`/`reorder`), each wrapped in `pg_advisory_xact_lock` for concurrent-edit safety. `election_day_voters` gained `not_voting_reason_id` (FK, `on delete restrict` - a reason in use can never be deleted), `not_voting_reason_set_at`, `not_voting_reason_set_by`.
- **One new permission**: `electionDay.manageNonVotingReasons`, gating only the "ניהול סיבות אי-הצבעה" catalog-management screen. By product decision there is no separate view permission - anyone who can see a voter's voted status also sees its non-voting reason.
- **New UI**: `NonVotingReasonsModal.tsx` + `useNonVotingReasons.ts` (mirrors `RoleManagementModal.tsx`'s precedent exactly), a reason dropdown in `ElectionDayContactModal.tsx`, a reason subtext under the voted/not-voted badge in `ElectionDayRow.tsx`, and a reason filter in `ElectionDayFilters.tsx`.
- **A permission-catalog-growth tension resolved deliberately, not by weakening a test**: `smoke-permissions.ts` previously asserted "the seed manager fixture has every `ALL_PERMISSIONS` entry." A brand-new permission is never auto-granted to the historical, already-applied Phase-0 seed (an admin opts a live role into it via "ניהול תפקידים" after the fact) - so the test was updated to encode this exception explicitly (`PERMISSIONS_ADDED_AFTER_PHASE_0`) rather than either failing or being loosened silently.

**Verified**: `tsc -b`/`eslint`/`build` all clean. 13 smoke suites pass (11 pre-existing + 2 new: `smoke-non-voting-reason-normalization`, `smoke-non-voting-reason-management-logic`). Live-verified directly against the real database post-migration (31/31 RPC-level checks: full catalog CRUD, duplicate-name rejection, `REASON_IN_USE`/`REASON_NOT_FOUND`/`REORDER_ID_MISMATCH` rejections, FK-restrict on a real voter assignment) and again post-deploy in production via a full Playwright run against the real UI (21/21 checks: assigning a reason, the "saved" toast, persistence across refresh and logout/login, the dropdown correctly hiding once voted=true while the reason stays in the database, reappearing with the same value after un-voting, the reason filter, plus regression coverage for role management, reminders, and search - 0 console/page errors). All temporary test accounts/roles/reasons were created via RPC and removed immediately after; the real 1,928-voter dataset and the real `PermissionUser`/role roster were confirmed unchanged (counts returned exactly to baseline) both times.

**One gap found during production verification, not resolved by this deploy**: the DB-side role-permission validator (`election_day_is_valid_permission`, defined in the earlier Dynamic Roles Phase 2 migration) was never updated to recognize `electionDay.manageNonVotingReasons` - confirmed live (`election_day_create_role` correctly rejects it with `INVALID_PERMISSION`). This means **no role can currently be granted this permission**, so the "ניהול סיבות אי-הצבעה" screen, while fully built and RPC-verified, is not yet reachable by any real account in production. The catalog RPCs themselves are unaffected (they have no caller-identity check, by design, same as every other Election Day catalog RPC) - only the write-path allowlist used when _saving a role's permission set_ is missing the new string. Fixing this requires a follow-up migration (`create or replace function election_day_is_valid_permission` with the permission added to its allowlist array) - not yet written or applied, pending approval.

## 2026-08-06 - Election Day: Dynamic Roles & Permissions - real role management (Phase 2)

**Status: production deployment complete.** Shipped as commit `92e8162` ("feat: add dynamic role management (Phase 2)"), pushed to `origin/master`, deployed to `https://kolbox-gamma.vercel.app` (Vercel Git integration auto-deploy, deployment `dpl_GCJJkBDLJWtDHm4AEYguCbJiYP3C`, `target: production`, `readyState: READY`, created ~1 minute after the push).

Adds real role management on top of Phase 1's read-only catalog: a "תפקידים" UI tab (create/edit/clone/delete a role) and a new path to create a `PermissionUser` against an arbitrary `role_id`, not just the 3 legacy checkboxes.

- **5 new RPCs** (migration `election_day_dynamic_roles_phase2`): `election_day_create_role`/`election_day_update_role`/`election_day_delete_role`/`election_day_clone_role`/`election_day_create_permission_user_for_role`, plus a DB-side permission allowlist (`election_day_is_valid_permission`, mirrors `ALL_PERMISSIONS`) that rejects - never silently drops - an unrecognized permission string on a write. `election_day_login`/`election_day_list_permission_users`/`election_day_create_permission_user` all extended to also return `role_id`.
- **Approved capability guard, enforced DB-side in the same transaction as the write**: `updateRole`/`deleteRole` reject an operation that would remove `electionDay.manageRolesAndPermissions` from every _actually-assigned_ user (a real join+count against `election_day_permission_users`, never merely a role's existence), serialized against concurrent calls via `pg_advisory_xact_lock`. `createRole`/`cloneRole` carry no such restriction. `deleteRole` also rejects (`ROLE_HAS_ASSIGNED_USERS`) any role that still has assigned users, ahead of the Phase 0 `ON DELETE RESTRICT` FK backstop.
- **A necessary architecture correction**: Phase 1's session resolution matched a session against the catalog by its legacy role text (`legacyRoleKey`). A `PermissionUser` created against an arbitrary dynamic `role_id` has no legacy text (`role: null`) - matching by legacy text would fail to resolve, or mis-resolve, such a session. Fixed by switching `resolveSessionRole`/`computePermissions` to match by **`roleId`** instead (`role_id` has been `NOT NULL` on every row, legacy or dynamic, since Phase 0) - one correct resolution path for every account. `ElectionDaySessionUser`/`PermissionUser` both gained a `roleId: string` field; `role` is now `PermissionRole | null`.
- New UI: `RoleManagementModal.tsx` + `useRoleManagement.ts` (the "תפקידים" tab, gated on `electionDay.manageRolesAndPermissions`); `PermissionUsersModal.tsx`'s 3 hardcoded role checkboxes replaced with a single picker built from the live catalog (built-in and dynamic roles alike).

**A real bug was found and fixed during pre-commit live verification**: `election_day_update_role`/`clone_role`/`create_permission_user_for_role` each declare a `returns table (id uuid, ...)` - PL/pgSQL treats those output columns as variables in scope for the whole function body, so a bare `id`/`permissions` reference inside was ambiguous between the table column and the output variable (`column reference "id" is ambiguous`, raised live). Fixed by aliasing every such reference to the table (`r.id`, `r.permissions`) before this migration was ever committed. **A second issue found and fixed the same way**: the two internal helper functions (`election_day_is_valid_permission`/`election_day_validate_role_input`, never meant to be called directly by the client) were still reachable by `anon`/`authenticated` after a `revoke ... from public` - this Supabase project's default privileges grant `EXECUTE` directly to `anon`/`authenticated` on every new `public`-schema function (not merely via the `PUBLIC` pseudo-role), so `anon, authenticated` had to be named explicitly in the `revoke` too. Both fixes landed in the migration file before it was committed; the live database matches the committed file exactly (verified via `pg_get_functiondef` comparison of all 10 relevant functions).

**Verified**: `tsc -b`/`eslint`/`build`/`git diff --check` all clean. 9 smoke suites pass (`smoke-permissions`, `smoke-permission-logic`, `smoke-permission-ui`, `smoke-bootstrap`, `smoke-role-normalization`, `smoke-role-catalog`, `smoke-election-day-scope`, `smoke-role-seed-parity` - all updated for `roleId`-based resolution - plus the new `smoke-role-management-logic.ts`, pinning the `electionDay.manageRolesAndPermissions` guard and the RPC-error-code → Hebrew-text mapping). Live-verified against the real database pre-commit (37/37 checks: role CRUD, dynamic-role login/capability round-trip, `ROLE_HAS_ASSIGNED_USERS`/`INVALID_PERMISSION` rejections, helper-function lockdown) and again post-deploy in production via a full Playwright run (27/27 checks: manager/dynamic-role login through the real UI, creating/editing/cloning/deleting a role, creating a `PermissionUser` against it, the delete button correctly disabled once a user is assigned, the dynamic role's exact permission set and `scope_type: "all"` both taking effect, 0 critical console/page errors). All temporary test accounts/roles were created via RPC and removed immediately after; the real 1,928-voter dataset and the real `PermissionUser` roster were confirmed unchanged (count returned exactly to baseline) both times.

**One residual verification gap, explicitly flagged, not resolved**: the `CANNOT_REMOVE_LAST_PERMISSION_HOLDER` guard's _blocking_ path (removing the capability from the actual last holder) could not be safely triggered live against production - any temporary role/user created for testing is never the _last_ real holder while the real manager account(s) still hold it, and forcing that scenario would require temporarily mutating a real role or account, which was not authorized. The non-blocking path (removing the permission from a role while real holders remain elsewhere) was exercised repeatedly and passed; the guard's SQL is structurally identical to the already-tested `ROLE_HAS_ASSIGNED_USERS` check.

## 2026-08-05 - Election Day: Dynamic Roles & Permissions - permission-engine read-path cutover (Phase 1)

**Status: production deployment complete.** Shipped as commit `b3ce9b9` ("feat: cut election day permission engine over to dynamic roles"), pushed to `origin/master`, deployed to `https://kolbox-gamma.vercel.app` (Vercel Git integration auto-deploy, deployment `dpl_BbCLGPtefzD8CzEHvdtApUhsSThQ`, `target: production`, `readyState: READY`, created ~1 minute after the push - no other push occurred in between, so this is the deployment for this exact commit).

Cuts the permission engine's read path over from a hardcoded `manager`/`operations`/`voting` → permission-set map to the live `election_day_roles` catalog (seeded in Phase 0), with a fail-closed contract as the non-negotiable requirement: every failure mode (catalog not loaded, a load error, a session role with no matching catalog row, a resolved role with a missing/unrecognized scope) denies access - none of them fall back to showing everything or to manager-equivalent permissions. No UI change. No change to how a `PermissionUser` is created (still the legacy 3-checkbox `election_day_create_permission_user` RPC). No change to the login/session model, to any other main-app role, or to `legacy_role_key`/Phase 0's seed values.

- **New RPC `election_day_list_roles()`** (migration `election_day_list_roles_rpc`): read-only, `STABLE`, `SECURITY DEFINER`, `set search_path = ''`, schema-qualified references, `EXECUTE` granted to `anon`/`authenticated` - the same lockdown/grant pattern as every other Election Day roster RPC. Returns exactly `id`/`name`/`description`/`permissions`/`scope_type`/`scope_value`/`legacy_role_key`, nothing more. Its own comment documents that anon access is the same already-accepted "no caller-identity check" limitation as `election_day_list_permission_users()` - not a new gap, not a login-model change.
- **API-boundary validation, never a blind cast** (`src/permissions/roleRecordMapper.ts`): every raw RPC field is validated independently - `permissions` filtered against the live `ALL_PERMISSIONS` catalog (an unrecognized/stale string is dropped, never cast through); `scope_type` accepted only as `"all"`/`"assigned_to_me"`, else `null`; `legacy_role_key` accepted only as a real `DatabaseRole`, else `null`; `scope_value` passed through as `Json | null` (unused, reserved). A corrupted or stale DB row can only ever under-grant, never over-grant.
- **Role-catalog state machine** (`src/permissions/roleCatalogController.ts` + `roleCatalogStore.ts`): explicit `idle`/`loading`/`loaded`/`error` states, an in-flight guard so concurrent callers trigger exactly one fetch, and an explicit `retry()` - a single failure never permanently locks the catalog, but there is no automatic/unbounded retry loop either.
- **`computePermissions`/`resolveSessionRole`/`hasPermission`** reworked to take the live catalog + its status instead of a hardcoded map; `EffectiveRole` (the old fixed 3-value union) and `PERMISSIONS_BY_ROLE` are gone. `useElectionDay.ts`'s `scopedContacts` (now `electionDayScope.ts`'s `resolveVisibleContacts`) keys off the resolved role's `scopeType` instead of `role !== "user"/"voting"` - fail-closed the same way.
- `src/services/supabase/database.types.ts` gained the `election_day_roles` table and `election_day_list_roles` function types (a Phase 0 gap, fixed here).

## 2026-08-05 - Election Day: Dynamic Roles & Permissions - database foundation (Phase 0)

Started a new, separate initiative on top of the just-closed Stage 1-4 permission engine milestone: replacing the hardcoded `manager`/`operations`/`voting` 3-role model with a fully editable, DB-backed role catalog (create/rename/clone/delete a role, assign it an arbitrary permission set) - approved product decisions: no protected roles (every role, including the three built-in ones, stays fully editable), the "ניהול תפקידים והרשאות" permission (not a role name) must always be held by at least one user, deleting a role with assigned users is always blocked, and role scope ("תחום עבודה": all contacts vs. only-mine) is modeled as a type+parameters pair so a future dimension is additive rather than breaking. Rollout is 4 independent phases, each individually testable/deployable/rollback-able - no big-bang cutover. This entry covers Phase 0 only; see `CURRENT_STATUS.md` for the full 4-phase plan and the phases still to come.

Phase 0 is a **purely additive schema foundation with zero behavior change** - nothing in the app reads from it yet:

- New migration `election_day_dynamic_roles_phase0`: creates `public.election_day_roles` (RLS-enabled, zero policies - same lockdown pattern as `election_day_permission_users`, access only via SECURITY DEFINER RPCs in a future phase) with `name`/`description`/`permissions text[]`/`scope_type` (`'all' | 'assigned_to_me'`)/`scope_value jsonb` (reserved for a future scope dimension)/`legacy_role_key` (temporary migration-bookkeeping anchor only, never shown in any UI, never touched by role editing - removed in the future Phase 3 cleanup).
- Seeded exactly the 3 roles that exist today (מנהל/משתמש/נציג קלפי) with permission sets and scope copied verbatim from `PERMISSIONS_BY_ROLE`/`scopedContacts` - byte-for-byte the same access any existing account already has.
- `election_day_permission_users.role` made nullable (a future dynamic-role user has no legacy text equivalent to store there) and a new `role_id` column added, backfilled via `legacy_role_key` (never by name, never by a hardcoded id), verified 100% backfilled before being set `NOT NULL`, with `on delete restrict` as the DB-level backstop that makes "can't delete a role with assigned users" unbreakable rather than just a polite RPC check.
- `election_day_create_permission_user` updated to also resolve and write `role_id` on every new row - frontend call shape (`p_name`/`p_password`/`p_role`) completely unchanged.
- `electionDay.manageRolesAndPermissions` added to the TS `Permission` catalog (`src/permissions/types.ts`) and granted to `manager` - inert today, not yet checked by any call site, included only so the DB seed and the TS catalog agree from day one.
- Whole migration wrapped in explicit `begin;`/`commit;`, same reasoning as the Stage 4 voting-role migration: the Supabase CLI's migration runner pipelines a file's statements rather than implicitly wrapping them in a transaction, so a failure partway through (e.g. after `role_id` is added but before the backfill/`NOT NULL` steps complete) could otherwise leave the table in an inconsistent intermediate state.

**Verified**: migration confirmed applied on both local and remote (`supabase migration list --linked`). `scripts/smoke-permissions.ts` extended with assertions for the new catalog entry (142 → unchanged pass count plus the new checks). `tsc -b`/`eslint`/`build` clean. Production smoke-checked read-only after deploy (HTTP 200, no data queried or changed) - the real 1,928-voter dataset and the real 4-account roster were not touched by this migration in any way (it only adds a new table and a nullable/backfilled column, never modifies existing `election_day_permission_users` data beyond that backfill).

Shipped as commit `d830d50` ("feat: add dynamic roles database foundation"), pushed, deployed to `https://kolbox-gamma.vercel.app` (`dpl_82Zi7jm44zEGAf9iU3BfmTFuSfoM`, created ~74s after this commit's timestamp, target `production`, `readyState: READY`).

## 2026-08-05 - Election Day: voting is now a real, loggable-in role (Stage 4)

Closed the last gap left open by Stage 2's notes: `voting` could only be exercised through the dev-only harness because no `DatabaseRole` mapped onto it - `election_day_permission_users.role` still only accepted `manager`/`user`.

- New migration `election_day_voting_role`: widens the `role` CHECK constraint (looked up dynamically via `pg_constraint`/`pg_attribute` by actual column reference rather than by text-matching the rendered constraint definition, so a future unrelated constraint that merely mentions "role" can't be mistaken for it - aborts instead of guessing if more than one match is ever found) and `election_day_create_permission_user`'s validation to accept `voting` alongside `user`/`manager`. The other three roster RPCs (`election_day_login`/`election_day_list_permission_users`/`election_day_delete_permission_user`) are role-agnostic and untouched. Wrapped in explicit `begin;`/`commit;` - reading the installed Supabase CLI's own Go source confirmed its migration runner sends a file's statements as one `pgconn.Batch` (wire-protocol pipelining for round-trip efficiency), not an implicit transaction, so without the explicit wrapper a failure between the constraint drop and re-add could have left the table with no CHECK constraint on `role` at all.
- `PermissionRole`/`NewPermissionUser.role` widened to include `"voting"`. `resolveEffectiveRole()` gained an explicit `voting → voting` branch ahead of the legacy `user → operations` catch-all - the permission engine itself (`PERMISSIONS_BY_ROLE`/`hasPermission`/`computePermissions`) needed zero changes, since it was built voting-aware back in Stage 1.
- `useElectionDay.ts`'s `scopedContacts` now restricts a `voting` session to its own coordinator's contacts, exactly like `operations` (approved product decision: voting and operations share the same record scope - the only difference between them is the permission set, not which rows they can see).

- Fixed a latent sort-comparator bug surfaced by adding a third role: `PermissionUsersModal.tsx`'s roster sort returned a non-symmetric result for two different non-manager roles (always `1` regardless of order), which is undefined behavior for `Array.sort`. Now: manager always first, stable insertion order otherwise.
